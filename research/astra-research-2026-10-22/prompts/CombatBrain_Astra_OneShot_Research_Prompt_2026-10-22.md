## 3. 必须尊重、也允许有证据地质疑的产品基线

以下是委托时基线摘要，完整台账及其后续明确裁决优先：

- 首版同时交付敌军增强和玩家 F6 托管，允许敌我独立启停；正常 Campaign 野战、多领主军团野战、实际可用的安全动态 Formation 拆分/合并/按能力重编及 MCM 开关是硬范围。
- 玩家有效直接命令和真实授权范围优先。采用稳定合法指挥域与动态 Formation 授权集合；观察范围不等于可写令范围。不可假定 Team、领主、Party 和指挥域一一对应，不能仅凭 `IsAIControlled` 推断 F6 授权。
- 对合法授权的 Formation，CB 独占战术决策权；可以复用原生 Tactic/FormationAI/Behavior 接口和底层 Order 执行机制。不得让另一个 Native 战术决策者长期并行改写任务，也不等于已经批准全命令域 Harmony Full 拦截。
- 只做 Commander/Formation 层，不修改 Agent 个体战斗、逐兵 AI、寻路或个人溃逃。首版允许保留原版士气/个体溃逃，必须在正常规则下验证指挥效果。
- Commander 是全局 Intent 和正式任务生命周期的唯一战略权威。Formation 按 TaskContract 和职责感知 Local Safety Envelope 局部应变；任务取消不自动解除持续职责，也不自动允许撤退。
- 存在有条件的极端危险紧急例外；对明示牺牲性关键职责，不能只凭高伤亡、兵员少或预计将全灭而自行解除。有效职责已经实质无法履行等严格条件仍须具备可观察依据。
- 战术评价采用合法性/可行性筛查、相对当前计划的全局净价值比较和不确定性处理。当前计划必须参与比较；考虑职责失守、转换成本、必要牺牲及失败后果，不能伪装成未经校准的精确胜率。
- 机会来源为共享稀疏战场关系与有限可组合检测器；允许主动施压创造机会，但不能把预测的敌军反应当事实。
- 标准原版兵种多维画像在研发阶段离线生成，Formation 运行时轻量聚合真实状态；未知兵种须可保守指挥，Vanilla Combat 与 RBM Combat 分别校准。
- 战术效果预测与校准以真实游戏引擎内交战为核心证据，机制推理、静态画像和游戏外模型只能辅助。受控 Mission 采样不替代真实 Campaign 集成验收，特殊“死战不退”测试不能直接外推正常士气。
- Commander 能力基于当前合法指挥域内合格参战成员的最高原版 Tactics；不扩大权限、不刻意犯错或额外延迟低技能反应。合格成员与变化处理细节仍待定。
- 反馈采用少量独立健康维度和重大变化事件；健康维度不是新的任务权威状态机，事件不等于自动重规划。运行时反馈不依赖 CBATH 旁路日志。
- 计算预算不足先削减额外候选、预测与昂贵诊断，不能牺牲玩家权限、关键职责连续性、基本反馈和安全交还。
- RBM Combat 是优先兼容方向，RBM AI 同时指挥不是首版硬要求。Limitless 大规模/万人兼容为条件式首发目标，不能因能采样很多 Agent 就推断能可靠指挥。
- 当前研究不直接修改 master、生产代码、现行 P3 合同及历史验收口径。历史有限 PASS 不证明整个产品可发布。

你可以论证某项已确认要求代价过高、相互冲突或需要重审，但要单列“建议重审的产品决定”，给出具体反例、证据、替代和范围影响；不要静默删改硬要求。不要重新让我逐项选择 A/B/C。

工程偏好：采用满足目标的最小充分机制。进程内运行时反馈不天然需要复杂分布式消息系统；只有发现对应失效风险才增加 ACK、持久化、Lease、事件总线或新 Registry。说明现有数据结构为什么不能承担责任，再提出新增模块。同步权威快照、版本校验和有界通知若已经足够，优先采用。可靠性不能靠无限叠加管理器换取。

## 4. 第一部分：完整覆盖、重点深入的独立审计

先建立“需求—设计—实现—证据—缺口”矩阵和决策依赖图。覆盖所有主要层，但把推理集中在最可能阻碍构建与效果的风险，尤其检查以下交叉问题：

1. **战场事实与能力**：可观察字段、新鲜度、未知值、装备分布、混编子群、弹药/伤亡动态、Vanilla/RBM 模型适用性。静态画像是否足以支撑任务效果预测，哪些数据仍需实机。
2. **机会、预测与评价闭环**：如何从当前态势生成可行状态目标和协同候选；预测器的数据从何来；当前计划与新计划怎样公平比较；如何避免循环定义、局部收益重复计数、只重击杀、僵持不动或无限试探。
3. **任务、持续职责与局部安全**：Task/Action/Duty/Intent 的边界与生命周期；关键职责交接、明示牺牲、客观失能的可观察依据、协同依赖环、多个编队同时自保、无安全路线等是否形成矛盾。
4. **反馈与重评稳定性**：健康快照和事件身份/版本/新鲜度、事实与推断、重复/乱序/缺失处理、必要消费确认、旧消息丢弃；单一生命周期权威；紧急局部动作与低频 Commander 解耦；避免每条事件引发全军换令。
5. **实际执行与控制权**：CB 战术独占、原生接口复用、合法域/F6、双端启停、故障交还、不同命令域、旧候选复活和版本检查能否统一。源码存在 Hook 不等于真实全覆盖；不能用反复抢写掩盖双 Writer。
6. **动态重编、军团与增援**：Formation 槽位及身份复用、拆并中的任务/职责/授权迁移、部分成功和引擎失败、玩家中途接管、MCM 关闭、援军整合。不假设引擎提供原子事务或任意回滚。
7. **规模、预算与降级**：按 Formation、关系边、候选和观测成本解释复杂度；检查隐藏的逐 Agent 全扫描、全对全比较和事件风暴；提出有界工作量与监测办法，保留毫秒预算待实测。
8. **验证可信度与交付路径**：现有 P0–P3 的真实覆盖与空白、CBATH 自证循环、受控 Mission 和真实 Campaign 的边界、基线开关、正常士气、双端独立对照、重编和 Mod 组合，如何避免把“发了命令”算作“战术有效”。

每个重要发现使用固定条目：`ID / 问题 / 适用基线与位置 / 证据类别 / 触发反例 / 影响 / 根因 / 推荐修正 / 替代与代价 / 依赖 / 如何验证 / 置信度`。

区分：设计矛盾、资料不一致、阶段内实际缺陷、未实现但已规划的能力、待运行验证的假设。不能把尚未到阶段的新功能缺失都叫 Bug。没有足够证据时可以结论“合理但未证”或“目前无法判断”，不凑问题数量。

完成“检索发现→具体设计决定”的追踪：对于最终方案的关键机制，指出哪份资料改变了你的选择，或它是依据本项目约束推导的原创建议。若一项外部成果没有改变任何设计、不构成有效对照，也不帮助验证，可以移到附录或排除。研究范围覆盖业界和学术的可迁移方法，不能只重复本提示词给出的入口；也不要为凑新颖性换掉已合理的设计。

## 6. 第三部分：形成一套连贯、可审议的参考设计

基于现有基线和证据，提出你推荐的最小充分设计，并与现有架构做差异表。不要只罗列“可考虑加入”的新功能，也不要为了统一而重造全部系统。优先复用已有合理设计，说明什么可保持、什么需补充、什么应替换或取消。

至少提供：

1. 一张分层架构/数据流图及权威归属表：谁拥有状态、谁只能报告、谁能改任务、谁能实际写令、谁能恢复 Native。
2. 一套候选接口骨架或接近 C# 的伪代码，覆盖战场快照、任务/职责、预测与评价结果、健康报告/重大事件、执行权限门和重编身份迁移。字段须有语义、生产者/消费者、时效和失败处理；不必堆砌字段或新增并列管理器。
3. 一条可执行的决策流水线：生成候选→权限/能力/可达/时间/依赖筛查→条件化效果预测→与当前计划比较净价值及不确定性→维持/局部调整/整体切换→职责承接→执行→反馈。说明计划延续与主动打破僵持如何兼顾，预测数据不足时怎样诚实降级。
4. 一个统一任务生命周期模型，配合非权威健康维度和有限局部行为记忆；解释如何迁移现有 `TaskFeedback`、`PlanLedger` 与 P3 专项测试路径，防止新增竞争状态机。所有生产/P3 迁移均为提案。
5. 局部安全和牺牲职责的判定结构：哪些是事实、预测、失能证据；哪些动作可在包络内立即执行；何种情况请求 Commander；权限失效和 CB 自身故障分别怎样处理。
6. 性能策略：有限候选、稀疏关系更新、缓存失效、脏标记/调度、事件聚合和降级顺序。区分算法成本推导、经验估计与待测数值。
7. 少量有明确价值的新增设计。分别标明“已有原则的具体化”“真正新增建议”“与现行基线冲突的替代”，比较收益、复杂度、数据条件和最快否证实验。不要默认引入训练型 AI、LLM 或 Agent 改动。

至少把“维持现有架构并补合同”“有针对性的局部重构”与必要时的另一实质方案进行比较。若不需要第三方案，说明原因。公式只能作为可校准候选；不能用自选权重、精确概率或臆测的游戏常数制造确定性。

### 6.1 战术智能必须推进到可追踪的计算过程

对于推荐的最高优先机制，不能只写“使用 Utility”“建立影响图”“进行有限预测”。至少说明下列关键问题中与你方案有关的部分：

- **候选从哪里产生**：由可观察的威胁/弱点和目标状态产生哪些有限变化；如何从目标匹配 Formation 能力、任务组合与协同条件；没有天然机会时怎样有限施压。给出候选结构、生成/剪枝过程、候选上限由什么约束及无候选回退，不把几个完整战术脚本包装成通用生成器。
- **怎样预测任务效果**：任务条件化效果的输入、输出、适用范围、事实/假设/不确定性；没有校准数据时采用何种保守表示和能力边界。可比较区间、序关系或有限情景等方式，不强制输出精确概率。已有离线画像、轻量机制分析与未来真实交战数据怎样分工，如何检出模型过期/失配，避免用自造战斗模拟器生成“证实自己”的证据。
- **怎样分配部队**：防止同一 Formation/兵力/时间窗口被多个候选重复占用；同时考虑主攻、牵制、保护和预备队；任务依赖不满足、能力不足或关键执行保障不可得时如何撤销候选承诺。明确选用何种有界分配算法及其不足。
- **怎样比较价值**：权限和硬约束先于效益；当前计划与候选使用可比较的状态基线和时间范围；包含到达/展开/交战/换令成本和失败后果；避免敌军威胁消除、击杀和职责收益的重复计数。若收益无法可靠区分，说明保留当前计划、有限试探或请求更多观测的选择条件。
- **怎样适应敌军**：只基于允许观察到的部署/行动考虑有限反应情景，不读取隐藏意图；敌军不配合、突然反制、机会短暂和双边 CB 同时调整时如何处理。记忆只用于当前战斗内必要的状态与失败记录，不擅自引入跨战斗学习。
- **怎样保持稳定与主动性**：计划承诺、切换收益、滞回、最小证据、未完成投入、无新信息的重复失败记忆如何协作。不能让防抖无限保护已经失效的计划，也不能每出现局部风险就重启全军。
- **怎样映射 Tactics**：在已确认约束内，提出候选覆盖、组合深度或情景处理等能力预设方式；共享相同权限、安全与反应基本保障。哪些映射只可作为候选，哪些需要体验/成本校准。

给出至少一条完整工作示例：输入战场快照→产生多个可行/不可行候选→拒绝原因→效果和不确定性→相对当前计划取舍→任务分配→关键依赖→局部执行/反馈→继续或改变计划。示例数值须注明人为构造，仅展示算法语义。不要用预先指定“正确计划”后倒推权重的方式假装完成选择。

### 6.2 可靠闭环必须给出操作语义

把接口进一步细化到以下操作的前置条件、状态变化、失败结果和可观察记录：

`Observe / GenerateCandidate / CommitPlan / AssignTask / ReportHealth / RequestReevaluation / EnterLocalSafety / ReplaceTask / TransferDuty / ReorganizeFormation / RevokeAuthority / ExecuteOrder / HandBackToNative`。

你可合并或改名以符合现有架构，但必须覆盖这些责任。说明每一步是否同步、是否允许重入或延迟、何时检查身份/权限/版本、失败后谁负责，保持有界工作量。不要默认游戏多线程，也不要强行引入线程；如确有异步路径，应指出真实来源。

职责有效性、任务生命周期、局部行为阶段和健康观察要能同时表达“推进受阻、牵制仍有效、伤亡很高、执行权限合法”。给出唯一权威来源，以及旧对象/槽位/任务版本如何失效。执行门不仅检查任务是否存在，还要保证当前授权和优先级有效，避免非法高优先候选在权限过滤前挤掉合法候选。

对于动态重编，提供前置检查、准备、可观测中间状态、身份迁移、任务/职责承接、失败后的合法保留或有限恢复，不假设原生操作可事务回滚。对于紧急自保和 Native handback，分别说明任务受阻、局部危险、权限撤销和 CB 自身故障的恢复路径。

### 6.3 补齐最小任务语义和引擎适配边界

请推荐首版足够可组合的最小 Formation 任务语义集合。每类给出目标、输入/对象、能力前提、持续职责、允许本地动作、依赖、进展/效果证据、失效/退出和原生命令映射需求。任务数量由覆盖需求决定，避免把每种战术各建一个不相干状态机。

把引擎依赖列成适配表：所需事实或动作、候选 API/Hook、证据所在和版本、已知能力、未验证部分、不可用时的降级、最小探针。源码静态可读到调用路径时给出路径；找不到对应能力时不要编造 API。缺少目标 DLL 不能成为拒绝设计纯 Core 的理由，也不能成为确认接管效果的依据。

### 6.4 新增建议必须说明实际贡献

额外检查机会窗口/ETA、反复试探的成本与失败记忆、职责依赖、预备队、射界/地形、弹药变化和增援是否存在尚未覆盖的高价值机制。可以提出更优新方法，逐项说明它补哪项缺口、属于已有原则具体化还是新需求、成本/风险、最小可否证实验及是否值得首版采用。

请主动删除重复或价值不足的候选机制。优秀的参考设计允许比现有设想更简单；不要以模块数量、模式名称或战术脚本数量作为“更智能”的依据。

## 7. 第四部分：对抗反例与后续最小验证计划

把高风险问题放进跨模块时间序列，逐步推演触发、各层决策与恢复；发现反例后回到参考设计修正。至少覆盖：

- 突破受阻但仍有效牵制，高战损与明示牺牲并存；
- 急迫危险时 Commander 尚未运行，多个编队同时局部脱离；
- 任务取消但职责仍有效，新任务尚未生效；
- 事件重复/乱序/丢失，旧任务报告或旧命令在换令后到达；
- F6 收回、敌我独立开关、权限暂空与故障交还；
- 拆并/槽位复用/增援与玩家接管同时发生；
- 诱敌无反应、窗口消失、不可达撤路、虚假机会；
- 未知兵种、混编、RBM 模型失配；
- 临界噪声造成反复前进后退、反复重试同一失败；
- 预算超载与观测日志故障，关键职责/基本反馈仍需维持。

给出最小而有区分力的实机验证清单：每项写清要区分的假设、场景、对照、独立读数、可能的反例、通过条件如何确定，以及需要的游戏接口/自动化工具。不能提供你没有运行过的实测结果。

明确区分纯 Core 逻辑测试、真实引擎内受控 Mission、真实 Campaign 集成、正常规则效果/性能测试。胜负/战损比较考虑双方兵力兵种、地形、攻防角色、种子、士气、玩家参与方式和 Mod 配置；比较 CB-vs-Native 等适用基线，配对/重复并报告不确定性，防止仅对自家对手有效。样本量和阈值给出设定依据或先导试验方案，不凭空签收固定数值。

最终生成按真实依赖排序的后续工作包，每包包含输入、预期产出、验收证据、阻塞和停止条件。第一批应优先消除最可能推翻架构的引擎/数据假设；同时给出无游戏环境下可先完成的工作。不改写现行 P3 合同，也不把“研究建议”直接登记成“用户已确认”。

## 8. 第五部分：必须构筑的小型可运行验证包

有本地执行能力时，请围绕上述参考设计中价值最高、最容易出现跨模块错误的 **2～3 个相连机制**构筑独立样机。默认优先覆盖：计划/职责连续性、权限和版本有效性、反馈与重评抑制，以及预算内候选比较的衔接。若审计发现更关键的组合，可以调整并说明理由。不要求实现整个 Mod，也不要搭建无关 UI、完整战斗物理或大型通用框架。

### 8.1 样机要求

- 先检查环境；适合时用与目标 .NET Framework 4.7.2 迁移兼容的 C# 纯 Core。若缺少合适编译环境，可用 Python 3 标准库编写可运行逻辑模型，同时提供关键接口向 C# 的迁移说明。不假装目标框架构建已通过。
- 样机必须具备明确输入、状态、操作、输出和检查命令。任务、事件和权限用结构化对象表达，不靠在用例中硬编码最终答案。
- 引擎通过窄适配器/假执行器隔离。假执行器只表达接受、拒绝、延迟、失效等接口行为；不能用它证明原生命令可靠执行或战术效果真实发生。
- 决策示例中的效果估计可来自显式构造的 fixture 或注入预测接口，必须标为人为假设。样机验证的是组合与决策逻辑，不是该预测值正确，更不是伤亡模型准确。
- 附 README，说明运行命令、依赖、数据结构、假设、覆盖范围、未覆盖引擎语义和迁移位置。环境能运行就实际运行、修正失败并保留简洁结果；不能运行就明确 `NOT_RUN` 和原因。

### 8.2 验证有意义的不变量和时序行为

从产品约束而非实现细节导出检查。至少覆盖与所选机制相关的以下性质，并明确未实现项：

1. 玩家/F6/双端开关导致授权失效后，旧候选、旧局部安全动作和旧任务都不能重新写令。
2. Mission/域/Formation 身份和任务版本变化后，延迟信息不能误作用于新对象；槽位相同不代表身份相同。
3. 重复通知不重复解除职责、重复创建后继计划或无限触发重评；有关键新事实时仍能够响应。
4. 取消行动不自动取消持续职责；职责要合法交接、明确接受空缺或按已批准例外处理。
5. 局部高伤亡/推进受阻不自动意味着全军失败；紧急局部动作无需等待完整重规划。
6. 同一资源不被重复分配；依赖环、不可执行协同或缺失关键职责不会被静默承诺。
7. 近似等价候选和临界噪声不会造成无意义振荡；硬失效也不会被冷却或承诺永久阻断。
8. 降低候选搜索/预测预算时仍保基本权限、关键职责与反馈；候选非法时不会排挤合法行动。
9. 未知和陈旧数据不会自动被视为安全、可达或有效；不同原因的降级可区分。
10. 局部任务、动作执行、职责效果和战果分层，不能通过自己的“成功标记”完成自证。

使用短事件序列、边界条件和必要的有限枚举/固定种子随机序列寻找反例；规模应适合复查。无需为普通 getter、常量或可由类型直接保证的细节堆积测试。

对于确实识别到的风险，尽量展示最小反例→候选修正→同例通过，并检查修正是否破坏其他性质。可移除一处关键守卫做负向校验，确认测试能发现错误；负向校验结果不能冒充生产 Bug。若无法构造真实已有实现的失败，应如实标为架构反例或假设风险，不捏造红绿测试。

报告用例数和实际失败/通过状态，不只给“全部 PASS”结论；提供关键事件轨迹和失败原因。检查通过只证明模型中列明的性质。

### 8.3 让“更合理的决策”能够被检查

在相同的构造输入下，比较现有可提取的纯逻辑、明确标注的简化旧规则或朴素反应式基线与推荐机制。只有真正执行过的代码才标为运行对照；简化基线不能冒充整个原版 AI 或现有 CombatBrain。

情景至少涉及：诱人机会与保护职责冲突、双方等待却不能无限僵持、敌方不按诱导行动、援军改变任务负担、资源不足以执行所有候选、已投入计划与略高分新候选竞争、未知能力和危险同时出现。依据所选样机范围，可对未实现部分给完整手工决策轨迹并标注。

评价重点是决策与硬约束是否一致、切换是否必要、是否会重复犯同一类错误、是否仍能采取有依据的主动行动。输出候选及拒绝原因、比较依据、最终行动、延续条件和后续反馈。构造场景不能证明游戏胜率提升，也不能只针对几个 fixture 写特判；应说明规则如何泛化，以及哪个尚未见过的反例可能推翻它。

## 9. 第六部分：把研究结果写成开发者能接手的规格

除了总报告，给出一份 `Proposed-Design-Spec.md`。优先把关键闭环写到开发者能够直接设计实现的程度：术语、模块职责、数据结构、操作合同、状态转换、错误语义、不变量、算法步骤、复杂度、适配边界、配置/参数及其待校准依据、迁移顺序和验收方法。

所有规则避免“适当”“及时”“足够大”“合理调整”等没有操作含义的结论。需要数值时，用有语义的配置参数、单位、边界及校准实验代替伪造的最终定值。协议逻辑通常可先确定；真实伤亡阈值、反应周期、性能预算等保持待测，不让一个未知阈值阻塞整个规格。

后续工作包应能独立派发：问题、对应推荐条目、前置输入、建议涉及文件/符号、所需接口、实现步骤、必须保留的行为、验收证据、阻塞和失败退出。至少把最先推进的工作包写到无需重新发起一轮总体设计讨论即可开始。不要承诺精确工时；用依赖和工作复杂度说明顺序。

提供“待游戏实测事项登记表”：假设、已有静态证据、如果为假会推翻什么、探针/场景、独立读数、判断方法、失败后备选。优先验证高影响且最不确定的假设，避免等系统全部实现才发现基本接管路线不可行。

对正式文档给出具体修订建议：在哪份 Charter/Requirements/Roadmap/研究台账增加或替换什么条款，依据哪个问题；标明仅为候选改动，不直接写入、批准或改写历史验收。完成需求→机制→规格→检查/实验→后续工作包的双向追踪。

## 10. 最终交付与质量要求

请交付以下成果，优先保存为可下载文件。工具能力客观不足时，以完整文本交付对应内容并标注未执行部分。各文档引用同一事实索引，避免重复抄写导致版本冲突。

1. `CombatBrain-Design-Research-Report.md`：自包含中文主报告，面向负责人判断方案和取舍。
2. `Proposed-Design-Spec.md`：关键机制的候选技术规格，面向开发实现。
3. `offline_prototype/`：小型可运行样机、结构化用例、检查代码、README 和实际结果/轨迹。没有执行能力时交付源码及 `NOT_RUN` 说明。
4. `Implementation-and-Validation-Handoff.md`：建议改动、最先工作包、引擎待证表、负责人待决事项和简短接续摘要。
5. `Evidence-Index.md`：已读仓库身份与材料、外部检索/证据索引和关键断言的来源。若内容短可并入主报告附录。

可生成文件时，把以上成果打成一个便于转交的压缩包，同时单独给主报告入口。聊天最终回复概述真正新增了哪些机制、最重要的发现、实际执行了哪些检查、仍有哪些限制，并附文件。不要只提供漂亮摘要而遗漏源码和规格。

主报告应包含：

1. 执行结论：总体合理性、最关键阻塞、最该保留的设计、推荐调整与当前无法判断之处。
2. 审查身份和覆盖：仓库/分支/SHA、已读材料、无法访问的内容、研究边界及文档时序冲突。
3. 需求—设计—实现—证据矩阵、关键依赖和按影响排序的发现。
4. 相关成果研究与逐项迁移判断。
5. 连贯的推荐参考设计、备选方案、接口/流程和相对现有设计的改动。
6. 对抗反例结果、实机待证事项、最小验证计划与分阶段工作包。
7. 必须由负责人裁决的少量问题：每项附推荐、依据、代价和未决原因；一般工程细节给出建议，不把一切退回提问。
8. 完整证据索引与检索限制。

主报告开头再给一张“实质增量表”：`原设计缺口 / 本次补上的具体机制 / 设计或运行证据 / 已收口到什么程度 / 尚需什么验证 / 对稳定性、智能或开发可执行性的贡献`。已有原则仅作背景，不冒领为新增成果。

交接摘要应让另一个 Agent 在没有本次对话的情况下接续：列出基线身份、最高优先发现、推荐顺序、待决事项，以及“哪些仍未被负责人批准/未实测”。

引用要求：仓库结论给文件路径、章节或符号，能提供时用固定提交链接；外部来源给作者、标题、日期/版本、可访问 URL 与对应论点。直接证据、来源声称、你的推论、建议和待验证假设清楚分开。用对方的宣传文案不能证明算法有效，用文档不能证明代码已经实现，用代码不能证明实际运行通过。

优先深度和可行动性，不为凑篇幅或来源数量扩展无关内容。最后做一次“断言—证据”核对、权限/职责/反馈一致性核对，并列出报告仍有的主要不确定性。

## 11. 执行顺序、停止条件与最后自审

建议按“能力与快照确认→快速覆盖和风险排序→围绕风险定向检索→构筑统一机制→样机与反例→回改规格→交付”执行。不要把全部时间花在读资料和做综述上，留足构筑、运行和修正的空间。可在完成一轮证据覆盖后冻结检索，将未解决的关键点单列；不要因追求穷尽而不交付可用方案。

将审计发现、机制构筑、反例审查作为相互纠错的步骤；不要编造多个专家或声称没有实际运行过的并行审查。若实际环境支持相关工作流，可使用其真实能力，但最终方案必须统一权威和接口。

交付前，以最苛刻的后续开发者视角回答并修补：

- 我是否真正读了本项目，而非写了一篇通用游戏 AI 文章？核心结论是否有固定基线位置？
- 是否有足够具体的推荐机制，或仍然只是“需要一个评估器/反馈系统”？
- 从快照到候选、比较、承诺、任务、执行、反馈是否存在无人负责的空档或两个权威？
- 在没有可信效果数据时，是否诚实退化，仍能完成基本指挥且不虚构智能？
- 样机检查是否能暴露错误，是否只验证自己写进去的答案？
- 是否用合成输入、静态测试或缺少真实权限的假适配器，过度声称引擎正确性/战术收益？
- 是否有新增的高价值思路，也有对过度设计和无效复杂度的删除建议？
- 不依赖你再参与，负责人和开发 Agent 能否识别该采纳什么、先验证什么、先实现什么？

完成标准是：在可获得证据下形成具体、连贯、可接续的推荐答案，展示已经执行的逻辑检查，并准确隔离仍须真实游戏验证的部分。若关键资料或工具不可用，交付最大可完成子集及精确限制；不以“不确定”逃避能推进的部分，也不伪造已完成状态。
