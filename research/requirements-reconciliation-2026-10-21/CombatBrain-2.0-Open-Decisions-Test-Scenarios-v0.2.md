# CombatBrain 2.0 — 待决事项、反例与可验收场景 v0.2

> 2026-10-21｜**研究与设计验收草案**，不是已经运行的测试、阶段 Exit Gate 或量化发布标准。与本研究分支的 Integrated v0.5、Charter/Roadmap Change Proposal v0.2 配套。  
> 依据：原始 Charter v0.3、Roadmap v0.2、Requirements Clarification（2026-10-20）；2026-10-19—21 用户已确认的跨话题决策。**测试场景是建议，具体阈值/对照数量/名单需要后续签收。**

## 1. 最先需要澄清的事项与完成定义

| ID | 尚需解决的核心问题 | 完成定义：需要获得的东西 | 分类 |
|---|---|---|---|
| U01 | 首版 Formation 任务语义最小集合是什么？ | 每个任务含合法输入、对象/区域、行为边界、前提、持续状态、完成/失败/阻断/取消判据、互依关系和必要日志 | 产品定稿 |
| U02 | 任务优先级、自主捕捉局部机会、紧急避险、违令如何裁决？ | 同一战局不同权限/损失/危险下的决策对照，不靠“AI 自己判断”绕过界线 | 产品 + 引擎 |
| U03 | 动态拆分/合并/重组的首版行为约束？ | MCM 开关、战前/战中、激战安全、人工接管、非法兵力、槽位不足、操作失败时均有明确的结果 | **首版产品 + 实机** |
| U04 | 多领主军团中的真实 Team/Formation 指挥权及 Tactics 来源？ | 对军团、分队、玩家手动与 F6、指挥者变更给出可复现读数；非授权兵力始终不受 CB 写令 | 实机查证 |
| U05 | 首版需证明到什么程度的组合、主动试探与有限反制？ | 明确必需示例、战术意图依赖、敌方不响应和计划失效时的正确处理 | 产品定稿 |
| U06 | 离线兵种画像如何制作并证明有效？ | 原版兵种装备套组、技能、输出/防护/机动维度、交叉对抗校准、版本信息、混编聚合和缺失回退试验 | 数据 + 研发 |
| U07 | 如何防止对短暂机会的过度反应？ | 有可达/不可达机会对照，能继续已有任务，也能因重大危险提前止损；切换成本与持续性证据可追踪 | 产品 + 测量 |
| U08 | 发布兼容范围准确包含哪些组合？ | 指定 Bannerlord build、原版/RBM Combat 配置、RBM AI 控制冲突处理、Limitless 版本、地图/人数和不支持清单 | 实机 + 产品 |
| U09 | Commander、任务监测、Formation 与全场采样分别有多少成本？ | 按独立指标采样，测真实 CPU、帧时间、响应延迟和失效情况；明确允许降级/不允许降级内容 | 性能测量 |
| U10 | 指挥官 Tactics 差异如何证明？ | 来源、等级预设、可观察行为差异；无故意失误、感知削弱和人为延迟 | 产品 + 研发 |
| U11 | 如何证明比原版/（相关场景下）RBM 指挥更有价值？ | 正式测试前冻结的对照、样本、玩家水平、不同结果指标、置信区间/失败报告、归因规则及发布门槛 | 最终产品验收 |

推荐先完成 U01 的任务语义定义，同时技术侧**只读**核查 U03/U04 的引擎事实。一个决定尚不满足“目标、权限、失败反例、验收观测、兼容退路”时，不能把它标为完全收敛。

## 2. 场景表：任务契约与多阶段战术

| 编号 | 输入/反例 | 预期行为和必要观测 | 重点防止的假成功 |
|---|---|---|---|
| S01 持续保护弓兵 | 保护骑兵/步兵有可利用的散兵追击目标；敌骑同时威胁弓兵 | 保护职责不因小机会自动中断；日志及独立命令记录说明仍有有效拦截能力；威胁解除后可重新评价 | “追击杀敌多”冒充保护有效 |
| S02 牵制真实成败 | 友军步兵已接敌，但敌主力仍能转向阻拦包抄 | Commander 不把“步兵已接敌”标为牵制成功；侧击需等待、换路或放弃，并记录可观察条件 | 仅接敌距离触发固定战术阶段 |
| S03 条件形成后侧击 | 牵制有效，敌拦截骑兵远离且无法按预计及时到达 | 侧击可推进；对可达时间、攻击位置、敌可用拦截力量有证据；侧击条件中途消失应重评 | 骑兵“到了目标点”就算成功 |
| S04 试探敌军回援 | 一次试探有回援反应，另一次完全没有反应 | 采取不同的计划分支；不设敌军必须上钩的假定；失去价值时安全终止 | 试探等固定秒数自动升级进攻 |
| S05 局部机会但主职责不变 | 掩护骑兵附近出现易攻击目标，攻击后仍可继续保护 | 授权范围内 Formation 可自行短促行动；不得离开保护范围或撤销主要任务 | 将 Formation 低频等待误当高层规划完成 |
| S06 紧急自主与牺牲 | 牵制部队承受大伤亡但仍可阻敌；另一个样例已无法继续履职 | 前者不为自保擅自弃守；后者允许有限应急并报告 BLOCKED/FAILED；区分合规与结果 | 用伤亡阈值直接判违令或直接撤退 |
| S07 受挫后停止旧攻势 | 突破条件消失、原攻势将造成明显无谓损失 | 旧命令实际停止，必要局部撤回并保留可用部署；执行日志及位移/编队状态双证据 | 计划写“撤回”，士兵仍原地冲锋 |
| S08 避免横跳 | 左翼/右翼战术评价接近并交替微变 | 不反复掉头，除非新机会优势足够、既有计划失效或有重大危险 | 每次计划器运行都重发最高分命令 |
| S09 短机会可达性 | 弓兵暴露只持续短时间，骑兵到达明显更慢；另一个目标保持暴露较长 | 前者应当合理放弃或低成本处理，后者可转为行动目标；不承诺抓住所有战机 | 看到“暴露”就远距离急转 |
| S10 二阶反制边界 | 包抄后可能遭敌骑回援，评估退路/友军支援 | 只做有界反制检查，并能记录放弃理由；性能不随推演无限扩张 | “反应智能”演变成无约束反复递归 |
| S11 执行合规二维 | 步兵依令牵制但被击溃；另一次未经授权擅自追远 | 前者 FAILED 且未违令，后者记录越权或其可验证证据；被冲散且无法判断原因时标“不确定” | 将败仗都算命令违背 |

## 3. 场景表：玩家权限、重组与援军（首版硬要求重点）

| 编号 | 输入/反例 | 预期行为和必要观测 | 禁止行为 |
|---|---|---|---|
| S12 战前优化 | 玩家已有初始部署；Commander 找到值得调整的兵力分配 | 在合法控制范围内以最少必要改变完成调整；给出收益/成本理由并可撤销未生效计划 | 一开战即无条件重排全军 |
| S13 战中安全重组 | 两个目标需要独立兵力，局部编队未深陷交战 | 在可用槽位与安全条件下拆分/合并；条件不足则维持原编队并采用可替代战术 | 激烈交战时大规模频繁拆装导致士兵抖动 |
| S14 MCM 关闭重组 | 玩家关闭动态编队功能，或战中从开切关 | 后续不发起/继续非法新重组，正确处理已经排队的重组；现存合法编组不被强制回退（具体瞬态需测） | 开关关了仍继续偷偷改编队 |
| S15 玩家接管 F6 | 一支正在重组或等待订单的 Formation 被玩家手动接管 | **立即**取消 CB 待执行重组和相冲突命令；保留接管时当前编组及玩家新命令 | 强制回到初始编组、继续写令或过几秒才放权 |
| S16 混合指挥 | 玩家手动弓兵、F6 控制步骑；敌骑攻击弓兵 | Commander 可把弓兵当需保护对象，但不改变它的手动命令；只用可控部队制定保护计划 | 以协调之名将玩家弓兵设为 AI 托管 |
| S17 非法重组请求 | 想借用其他 Team、盟军无权限 Formation、玩家手动部队来补兵 | 重组前权限检查拒绝；已有战术应安全降级或转用别的合法编队 | 因统帅/领主映射误判把不归 CB 控制的人拉走 |
| S18 多领主军团 | 至少两个领主部队共同参战且权属/实际 Team 不符合简单一一对应 | 先正确读取统帅与实控权限，再形成协同计划；记录每一次命令对应的合法控制对象 | 假定每个领主永远有独立 Team/Commander |
| S19 原生援军加入 | 我军增援以不同批次入场，兵种、时间不可预测 | 未入场前不当作现成资源；入场后只把合法可控 Formation 纳入计划与画像动态聚合 | 更改原版援军数量/顺序/生成时间 |
| S20 玩家全军撤退 | 玩家下达撤退命令，CB 仍有继续进攻的计划 | 立即尊重撤退并停止相冲突的 CB 战术；局部单位后撤不得冒充全军退出 | AI 否决或重新覆盖玩家的撤退 |

## 4. 场景表：兵种画像、文化与 RBM

| 编号 | 输入/反例 | 预期行为和必要观测 |
|---|---|---|
| S21 同类型不同文化弓兵 | 在可比地图、敌军、人数、状态下比较长弓兵、重装弩兵、低级弓兵 | 因射程、射速/弹药、防护、近战和机动差异改变掩护需求、部署位置或任务选择；不能硬编码文化名 |
| S22 文化标签与实装相反 | 文化是巴旦尼亚，但军队实际几乎无合格弓兵 | 不强制选择弓兵主导战术；能力优先、文化只在合理候选之间微调 |
| S23 混编聚合 | 同一 Formation 包含不同文化兵种和弓/弩混编 | 射击输出、接敌风险、机动与持续性按实际组成评价，不以首个兵种或平均射程假装全部适用 |
| S24 未知/缺失画像 | 部分兵种数据库缺项，或装备数据临时不可得 | 首先保守降级并标置信情况，仍可做安全基础指挥；不把未知能力当 0，也不对其下过度自信的高风险特种任务 |
| S25 原版/RBM Combat 差异 | 同兵种使用相同装备，但 Combat 模型和配置不同 | 从相应离线画像载入并验证身份；模型不匹配时标记降级或拒绝宣称完整战术评估，不复用错误强度断言 |
| S26 RBM AI 与 CB 冲突 | 同时启用两套控制 Tactic/Formation 命令的 AI | 识别并避免双重发令；必要时明确互斥/禁用和安全退出，不能静默相互覆盖 |
| S27 “更丰富”对照 | RBM/原版已有的步兵保护、弓兵后撤、骑兵冲锋循环、散兵袭扰等 | 证明 CB 的任务跨编队依赖、条件反馈和能力差异带来可见的新协同结果，而不只把相似动作改名 |

## 5. 场景表：万人同屏与性能

| 编号 | 输入/反例 | 预期行为和必要观测 |
|---|---|---|
| S28 普通规模基线 | 原版正常野战，规模从小到约 2000 Agent 实际允许范围内分档 | 测 Commander 规划、状态采样、任务监督、Formation 执行各自成本及总帧开销；保持权限与行动准确 |
| S29 Limitless 大规模 | 指定版本 Limitless 的数千至更大规模，玩家可选的实际地图环境 | 检查能否加载、可用 Agent/Formation 数、命令落地、阵型宽度、地图空间、NavMesh、帧时间和稳定性 |
| S30 性能降级 | 超过目标负载或发生采样变慢 | 可以减少低收益战术候选/额外预测，必须保留基本任务连续性、合法权限、退出和必要监测；显式记录降级 |
| S31 地形无法容纳部署 | 狭路或地图过小，大 Formation 的包抄/盾墙不现实 | 任务/阵型适用性返回不可行，保留安全计划或替代方案，不能因为部队人数多而下不可能完成的命令 |
| S32 预备力量取舍 | 小规模无多余兵力，大规模拥有机动余量 | 不硬留固定比例预备队；只有明确后续价值才保留并及时投入，不因大规模环境改变基本规划架构 |

Limitless 是否首发发布**必须由 S29/S30 等专项实测及产品开发增量共同决定**；不能仅凭 Mod 已发布、能够加载或理论 Agent 上限宣称兼容。

## 6. 统一的证据采集与归因规则

每个场景至少记录：
- 运行身份：游戏 build、CombatBrain 提交 SHA、Mod 列表/版本及 MCM/Combat 配置、战斗模式、地图、攻防身份、原生士气与难度。
- 资源状态：Team/统帅和合法权限、玩家手动/F6 状态、部队编组、兵种/装备与离线画像版本、实入场人数及援军事件。
- 决策依据：同一时间基线上的 BattleState、候选任务、价值/风险/机会窗、关键前置条件、选择和拒绝原因；因果推断与观测事实分开。
- 实际执行：命令接收、Formation 成员/位置/面对/行为、命令持续时间、取消/权限交还、原生行为干预、违令判据与不确定项。
- 结果：任务实际效果、整体胜负、战损、玩家操作、性能分布、异常与回退、未验证项。不以 CB 日志单方自述代替独立观测。

**四层验收不得互相替代**：E1 控制权限和命令落地；E2 Formation 履职与任务合规；E3 战术效果；E4 整场真实收益。对于“牵制是否成功”等难以证明敌军动机的结果，只用可测的敌方运动/位置/机动能力和防线时间，不宣称精确掌握敌军意图。

建议采用同条件随机种子/地图/兵种/Combat 配置配对的对照，并分开比较原版 AI、CombatBrain、需要时的 RBM AI。额外开启 RBM Combat、修改士气或玩家亲自参战应作为控制变量单独分层，避免把 Combat 模型差异误归于 Commander。

## 7. 首版发布检查（草案，不是已通过）

- **硬门槛**：敌军增强、玩家 F6、正常战役野战、多领主军团野战、动态 Formation 重组与 MCM、合法玩家接管/退出，在完整且可复查的验收条件下分别达标。
- **设计和能力**：最小任务语义、跨编队反馈与安全止损、能力驱动兵种任务适用性、原生士气下有效行为；正式集合和门槛待用户最终签收。
- **条件式兼容**：RBM Combat 和 Limitless 的实际支持组合单独签收，未达标组合须说明不支持，不得从普通规模推定万人。
- **不在首版必要范围**：RBM AI 深度同启、广泛兵种 Mod 专项适配、攻城、Agent AI 改写、士气全面重构、复杂预备队轮换。
- **最终量化验收**：未先行冻结玩家样本、战场矩阵、响应/CPU 预算、战损/胜负阈值、有效任务率和失败披露规则前，不得宣称总体通过。

## 8. 文档收敛工作流

下一轮优先 U01，一次讨论一个关键问题。每确认一项同时产出：最终选择、拒绝理由、边界和反例、可观测验收、关联 Charter/阶段、依赖工程查证、版本来源。用户最后签收后，在独立 PR 正式修改 charter/ 的三个上位文件。本研究分支只提供审计依据，不自动关闭未决项。
