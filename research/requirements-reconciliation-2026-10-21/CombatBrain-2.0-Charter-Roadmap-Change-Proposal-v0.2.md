# CombatBrain 2.0 — Charter / Roadmap 修订影响与变更提案 v0.2

> 2026-10-21｜**研究分支建议，不直接修改正式 Charter、Roadmap、P0—P6 Exit Gate 或执行中任务登记**。  
> 原始目标资料：charter/Charter V0.2.md（正文 v0.3）；charter/CombatBrain-2.0-Development-Roadmap-v0.1.md（正文 v0.2）；charter/CombatBrain-2.0-Requirements-Clarification.md（2026-10-20）。  
> 对应本研究分支：CombatBrain-2.0-Requirements-Integrated-v0.5-DRAFT.md。将确认要求纳入上位文档需要单独的签收和受影响阶段评审。

## 1. 修订原则

- **产品决定、工程假设、测试结论三者不能混写。** 用户已确定“要做”，不等于当前代码“能做”。
- Charter 描述长期目标、首版必须有的能力和边界；Roadmap 定义分阶段建立与验证该能力的工作；Requirements 保存决策树、选择依据、反例及未确认条目。
- 不改旧 P0/P1/P2 的限定验收结论；现有 P3 任务的具体合同与 registry.json 优先于新建议。待阶段门调整获批准，再在专门变更中登记“影响的条款、范围和回归证据”。
- 当前分支仅新增研究文档。**不得把本变更单当作自动生效的派单**。

## 2. Charter 各章节拟增加的规范性内容

| 对应章节 | 应并入的用户已确认要求 | 还不能写成定案的部分 |
|---|---|---|
| §1、§19、§20 | 目标驱动的 Commander/Formation 战术提升；Agent 个人作战与个人士气行为不进入修改范围；敌军、F6 共享底层战术能力 | 不保证个体动作效果与队级命令总能吻合 |
| §5、§6 | 原版兵种研发期离线生成基础多维画像；运行时按当前 Formation 人数、状态、敌我关系聚合；原版/RBM Combat 支持不同校准配置 | 画像公式、误差界限、全兵种数量、RBM 当前具体可兼容配置待证 |
| §7、§9、§10、§11 | 允许主动制造局部优势、有限试探、牵制、突破、扩大战果；多阶段条件驱动；有限敌方反制；不穷举博弈树、不追逐所有短暂机会 | 一阶/二阶预测仅为设计解释，不预定递归深度和确切窗口数值 |
| §8、§12、§13、§23、§27 | Commander 分配以战术职责为中心的预定义可验证 Formation 任务契约；包含目标、任务重要性、自主行为边界、反馈与终止条件；Formation 任务内自主利用局部机会、有限应急避险、持续履职；结果失败与越权分开评价 | 最终任务枚举、权限阈值、紧急撤离判据、任务状态编码待详细设计 |
| §8、§12、§21、§29 | **动态 Formation 拆分、合并、重组是首版交付要求，必须有 MCM 开关。** 默认保留原编组；仅根据明确战术收益增量调整合法控制兵力。玩家接管后保留当前分组并立即停止 CB 在途重组/冲突命令；激烈接战原则上不做大规模重组，失败保持原状态 | 真正可安全重组的引擎时机、Formation 槽位、MCM 关停瞬态、性能开销需验证 |
| §14—§17 | 允许完整战场视野，但不偷读未执行命令或未来意图；Commander 规划/轻量监测/Formation 局部执行分工，有界降级；Tactics 影响评估与协调能力，不故意让低技能变慢或犯错 | 真实更新频率、技能档位、CPU 时间/延迟目标需实测和产品确认 |
| §18、§28 | 胜利优先、必要牺牲；首版可沿用正常原生士气和溃逃规则，Commander 应当识别局部溃逃并合理调整；玩家阵营全军撤退权不能被 AI 抢走 | 未来士气调整能否在不修改 Agent 前提下实现，不预作承诺 |
| §22—§26 | 上层战术表达优于简单固定文化战术：多 Formation 协同、可观察任务依赖与真实反馈；兵种能力优先、文化偏好次级，不追求无意义多样性 | “优于 RBM”的实战收益仍须比较验证，不能在文档自证 |
| §29 | 首版必须同时支持敌军 AI 增强与玩家 F6、**正常战役野战含多领主军团野战**；CustomBattle 作为开发/回归环境；首版优先标准野战、非攻城；按当前权限接管并安全交还；原生援军产生逻辑不改，仅纳入已入场可用兵力 | 多领主 Team 归属、战役 F6、规模/地图及具体覆盖矩阵待实机 |
| §29 兼容扩展 | CombatBrain 独立，不要求首版与 RBM AI 等双接管控制面共存；设计支持原版/RBM Combat 双画像。Limitless 万人同屏作为正式兼容目标，专项验证合格且额外成本可控时可随首版发布 | 不提前宣称已兼容 RBM Combat、Limitless 或自定义兵种 Mod；后者专项适配暂缓 |

**特别提醒：**旧 Charter §29.2 中“战役野战/F6 为建议范围”的措辞已落后于后来确认的首版要求；研究分支记录这些决定，正式修订时应显式更新历史条款和来源，不只是附加一段新文字。类似地，旧 Requirements 仍把多领主问题标成“当前讨论”，现在可标记为“首版必要，但实测归属待查”。

## 3. 建议的首版硬要求与条件式目标界线

| 项目 | 产品优先级 | 产品签收/工程证明关系 |
|---|---|---|
| 敌军 AI 增强 + 玩家 F6 | **首版双硬门槛** | 两端均须有独立战场验收证据 |
| 正常战役野战及多领主军团野战 | **首版硬门槛** | 统一 Commander 不等于自动拥有所有领主部队写令权限 |
| 动态 Formation 拆分/合并/重组 + MCM | **首版硬门槛** | 必须兼容玩家手动控制、接战安全、重组失败回退和控制权交接 |
| 合法任务契约、履职反馈、基础协同/止损 | **首版基本能力** | 最小任务集和最低战术组合待最终收敛 |
| 原版兵种离线画像、能力驱动战术差异 | **已确认设计路线** | 发布所需画像覆盖、精度、模型识别与回退 Exit Gate 待冻结 |
| 原版与 RBM Combat 分模型画像 | **架构要求** | 首版 RBM Combat 正式兼容支持范围需实测并签收 |
| Limitless 万人同屏 | **正式兼容目标、条件式首发** | 性能、槽位、实际战术效果和加载兼容验证通过且成本可控才能称支持 |
| RBM AI 及其他战术 AI 深度并用 | **不作为首版必要** | 要有冲突识别及安全的禁用/回退，不得双重抢令 |
| 广泛兵种 Mod、攻城、长期个人风格/LLM | **后续扩展/暂缓** | 未经批准不得通过设计稿扩大首版范围 |
| 完整士气重构、专门预备队轮换体系 | **首版不必需** | 不能因此影响已确认的基本士气响应/兵力调配 |

## 4. Roadmap P0—P6 的变更影响（先形成提案，不改旧阶段门）

| 阶段 | 建议增加的输入/活动 | 必须另行验证的独立证据 | 阶段门保留规则 |
|---|---|---|---|
| P0 工程基座 | 场景身份、原生 Team/Army/Formation 权限链和 MCM 基础读写；记录 Combat 模型/Mod 组合 | 游戏原生与重要 Mod 组合真实加载、权限只读映射、MCM 开关可被可靠检查 | 原 P0 限定执行通过不代表军团/F6/重组通过 |
| P1 最小指挥闭环 | 任务契约最小语义、任务状态与合规二维分离、可撤销命令路径 | 同场景不同目标/约束导致可观测行动变化；停止后旧动作不残留 | 不将“多个任务名”视为闭环已完成 |
| P2 多 Formation 协同 | 战术职责跨兵种分配、一个主职责、多目标贡献、玩家手动目标只读参与协同 | 不抢令、保护/牵制连续、前置依赖清晰，状态与权属可核 | 已通过三职责合同不自动升级为更广任务库 |
| P3 反馈/止损与重规划 | 前提失效、授权应急后撤、旧攻势停止、必要牺牲与违规分开记录 | 正反例中实际形成/取消命令，履职与局部效果有独立观测 | 当前执行合同不因研究草案被隐式改写；是否已达标以最新运行证据判定 |
| P4 主动权与有限博弈 | 任务组合、条件推进、试探/反制、机会可达性、切换成本、兵种画像用于候选排序 | 试探有反应/无反应、短机会/持续机会、不同画像同类型部队等对照，有真实行动区别 | 不以固定流程、硬计时或战术枚举计数过关 |
| P5 泛化与稳健性 | **首版必需**的正常野战、多领主军团、F6 混合控制、战前与战中安全重组/MCM、已入场援军、混编、正常士气；按矩阵实测 RBM Combat 和 Limitless | 场景/控制权/版本/阵型安全/性能矩阵，禁用时安全，重组失败保持合法编队 | 未测 Mod 组合和万人规模不能自动继承原版通过结论 |
| P6 最终体验 | 敌军对抗玩家、F6 帮助玩家、战损与胜率、任务/战术效果归因，文化与能力影响 | 对照原版 AI，必要时和 RBM AI 分组；控制 Combat 模型、难度、地图、士气，报告样本、置信与失败 | 无量化事先判据、不是真正双端验收，不准发布达标声明 |

**依赖警告**：动态重组被确认为首版硬要求，不代表必须倒回重做所有已验收阶段；可在适当开发阶段单列带验证与回归的工作包。本文不为 P0—P6 发出新任务卡，也不以“P5 再测”代替尽早发现 Formation 槽位或权限风险。

## 5. 必须保持的现行证据边界

- 2026-10-19/20 的原始 Roadmap 和需求文档记录了 P0/P1/P2 限定通过、当时 P3 未正式通过；**这是历史文档的时间截面**，不是本研究稿在最新 HEAD 上重跑测试的结论。
- 验收报告中“采样遍历 mission.Teams”不证明多领主 Commander 已正确识别全部队伍或指挥权；F6 控制链、玩家接管及重组瞬态未因此通过。
- P3 具有自己的任务登记与证据链。新需求决定应走单独的阶段影响评审，不可默默修改正在执行的代码合同或改变验收门槛。
- 原版士气可以沿用，但正式战场体验验证应在正常士气下进行；“死战不退”只作为隔离变量的实验条件。
- 兼容是一张具体 build × Combat 模型 × AI 控制组合 × 地图 × 人数 × Command 权限 的实测矩阵，不是单个“支持某 Mod”的笼统标签。

## 6. 正式修订前的审查清单

1. 明确“战术职责集合”的最小首版名单、每项前置能力、成功/失败/越权和退出条件。
2. 明确动态重组开启/关闭后的全部规则：初始部署、接战安全、授权集合、回滚/保持、玩家 F6 接管、控制槽位限制和观察指标。
3. 验证多领主战役 Team/Commander 权限映射、F6 与技能来源、援军重新分配。
4. 证明离线画像输入、版本管理、装备随机套组、静态/动态边界、原版/RBM Combat 双模型校准可行；低置信度时不中止指挥。
5. 分清可作为候选的 RBM 成熟 Formation 行为、不可移植的 Agent 行为，以及 RBM AI 同时运行时的抢令风险。
6. 测量原版规模和 Limitless 大规模的真实战场采样/指挥性能与几何可行性；制定允许降级与用户可见支持矩阵。
7. 为 P6 冻结预注册对照、胜负与战损指标、真实玩家水平/样本以及“确有 CombatBrain 指挥收益”的归因规则。
8. 完成决策来源与版本链接，正式修改 Charter/Requirements/Roadmap 时同步三者，不留同一条款“在这里已确认、另一处仍待定”的矛盾。

## 7. 审批与合并条件

研究分支只证明文本已存档；**不证明产品定稿、代码落地或兼容通过**。只有用户确认重大产品取舍、技术侧完成必要核查、文档冲突消除之后，才另行提出对 charter/ 下原始文件的正式更改。若仍有未定数值，保留明确的开放项而非自动填数。
