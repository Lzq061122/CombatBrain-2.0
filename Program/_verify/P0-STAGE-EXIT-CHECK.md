## 2. FD-PoC 适用范围

这些编号是功能草案中的引擎实验编号，和开发阶段 P0/P1 不同。

- **FD-PoC P1：不适用当前路线。** 它检查关闭 AI 后 Facing/Arrangement 残留覆盖；本批没有关闭 AI，没有实现这两个写令域。不能登记为已验证安全，也不因此补 Route B 或 Facing/Arrangement。
- **FD-PoC P11：当前 Movement Stop 范围通过。** 草案称融入原生 Behavior 的方案为 Route A，本批派单称 TCL C 路线，适用的是同一原生行为正向生效问题；不把命名差异当作另一个实验。
- **FD-PoC P2：当前适用的安全边沿仍未验证。** 需要按 C 路线核验控制资格变化后停止本方执行/撤权，而不是硬套 Route B 的释放租约判据。玩家接管、阵亡导致的控制变化应按实际触发逐项记录，不能验证一种后自动宣称两种都已通过。

当前 CBATH `CbathTools.cs` 的公开入口只有单向 `delegate_team_to_ai`，源码说明是把玩家队交给 AI，没有反向玩家接管入口。2.0 当前目标又明确排除整个玩家队。这解释了现有场次为何未触发该边沿，但**工具不可达不等于产品安全已验证，也不自动使阶段门槛不适用**。若当前控制范围使某种玩家接管场景从定义上不可达，应先把控制范围及该项适用性明确写定，再判断是否需要范围调整；本次不擅自豁免阶段门槛。

## 3. 退出前的最小剩余工作

剩余工作限定为**当前 Movement 通路的适用控制权/资格变化安全核验**：

1. 先落场景判据：同 Mission、同实际 Formation、同有限意图，明确控制资格变化的真实触发方式、时刻和前后值。区别“实际玩家接管”与“测试接口改变资格”；后者只能证明相应实机守卫分支，不能冒充完整玩家事件链。
2. 覆盖待执行命令遇到资格变化时不落地，以及已有本方行为在资格丢失后不再执行/撤权的适用路径。记录候选、获选/待转交、资格变化、否决/取消、写入计数和实际后值。把变化前已经写完、之后仅命中 already_written 的场次与资格守卫真正触发区分开。
3. 沿用 CBATH 进游戏；现有工具不能触发时，只考虑 2.0 仓库内该场景所需的最小适配，不改变冻结 CBATH 核心、不搭通用验证平台。先判断场景是否真实可达，再实现适配；不要机械地再次运行未改变触发条件的同一 Stop Demo。
4. 提交可复查的场景结果与 FD-PoC P2 适用域判定后，仅复核 Exit Gate 3，并更新阶段结论。Gate 1/2/4 与单槽位同步成果直接复用；只有受源码变更影响的事实才补查。
