## 3. 唯一新的阻挡：首次获选等待截止被重投刷新

脚本 §5.2 明定：SelectionWaitSeconds=10.0，从**首次提交候选**起算，不因重复回调重置；§6.3 要求超过10 s未获选使Plan失效。

本轮 P `plan-4-task-1` 的原始日志给出了实际失败：

| 事实 | 行号/时刻 |
|---|---|
| 首次候选提交 | L513，97.721 |
| 同任务再次提交 | L531，100.727 |
| 原定截止 | 107.721 |
| 过原定截止仍提交 | L581，109.742 |
| 最后一次提交 | L753，139.788 |
| 终止原因 | L756，139.934，FormationEligibilityLost（另一任务空编队） |

全场该任务候选共15次，REAL_SELECTION=0、WRITE_EXECUTED=0、TASK_SELECTION_TIMEOUT=0。从首次候选到关闭为42.213 s。后序任务持续 predecessor_not_written，等待问题不是实际获选或发令延迟。

来源明确：Host `SubmitPending` L336 每次执行 `task.SubmittedAt=now`；Core `SelectionDeadline()` 用 `SubmittedAt+10`；`SweepExpiredSelections` 读这一移动截止。`ExecutionGate.SubmitCandidate` L40也每次覆写 SubmittedAt。3 s重投总在10 s前刷新，两层不能把它当新任务重新起算。

最小整改为同一 task_id 固定首次候选提交锚点，重复投递不得延长等待期限；任务与执行门使用一致语义，过期取消/清槽/撤权，并使 Plan以 SelectionTimeout结束。普通资格和退出动作的既有例外不变；不修战术权重、强制获选或另建重试框架。晚到回调与最终写令也不能绕过该截止。只补能区分“重投刷新截止”的回归，按原 §5.5 复验受影响场次，不要求新增测试矩阵。
